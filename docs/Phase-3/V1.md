# Complete Guide: Next.js Google Ads Lead Capture System (Phase 3)

## Project Overview

Phase 3 evolves the lead capture system into a more realistic marketing attribution platform.

Phase 1 introduced:

- Conversion journeys
- Session-based conversion tracking
- GA4 events
- Duplicate conversion protection

Phase 2 added:

- Lead collection
- API validation
- PostgreSQL persistence
- Marketing attribution fields

Phase 3 improves how attribution is captured and managed.

Instead of collecting marketing information when the user submits the form, attribution is captured automatically when the visitor first lands on the website and is attached to the conversion journey.

The browser no longer needs to read `window.location`, `document.referrer`, or `navigator.userAgent` during form submission.

Everything comes from one trusted source.

# 1. Automatic Attribution Capture

The landing page automatically captures marketing information as soon as it loads.

```text
Landing Page

↓

captureAttribution()

↓

sessionStorage
```

Captured values include:

- gclid
- utm_source
- utm_medium
- utm_campaign
- utm_term
- utm_content
- landing page
- referrer
- device

The visitor does not need to click anything before attribution is preserved.

---

# 2. First-Touch Attribution

Phase 3 also records the user's original acquisition source.

```text
Landing Page

↓

captureFirstTouchAttribution()

↓

localStorage
```

Unlike session attribution, first-touch attribution is never overwritten.

Example:

```text
Monday

Google Ads

↓

utm_source=google
```

Later:

```text
Wednesday

Facebook

↓

utm_source=facebook
```

The current session changes to Facebook, but first-touch attribution remains Google.

This enables future first-touch vs. last-touch attribution analysis.

---

# 3. Session Attribution

Current attribution is stored in:

```text
sessionStorage
```

It survives page navigation during the current browser session.

If the browser session ends, the attribution is discarded.

---

# 4. Conversion Journey

When the visitor clicks **Get Started**:

```text
ensureConversion()
```

creates a conversion object.

Example:

```text
Conversion

├── eventId
├── createdAt
├── started
├── completed
├── fired
└── attribution
```

Notice that attribution becomes part of the conversion itself.

This keeps every conversion self-contained.

---

```text

```

Phase 3 changes this to:


Everything comes from one object.

Benefits:

- Single source of truth
- Less browser API usage
- Easier testing
- Cleaner code

# 7. Conversion Event Identifier

Each conversion receives a unique identifier.

```text
crypto.randomUUID()
```

Example:

```text
7c00cac8-f0e0-44bf-acd4-2eefb414cce3
```

This identifier:

- connects browser events
- connects database records
- connects GA4 events
- supports future offline conversion imports
- enables event deduplication

# 14. Phase 3 Design Decisions

## Why capture attribution immediately?

Landing pages often lose URL parameters after navigation.

Capturing attribution on page load ensures marketing information is preserved before it can be lost.

---

## Why attach attribution to the conversion?

Every conversion becomes self-contained.

Instead of multiple components querying browser APIs independently, all marketing context travels with the conversion journey.

---

## Why store first-touch separately?

Session attribution changes over time.

First-touch attribution preserves the visitor's original acquisition source, enabling more advanced attribution analysis in future phases.

---

## Why store `event_id`?

A stable conversion identifier allows browser events, database records, and analytics events to reference the same conversion.

This is especially useful for debugging, deduplication, and future server-side or offline conversion workflows.

## Summary

- Attribution is captured automatically when the landing page loads.
- First-touch attribution is stored once and never overwritten.
- Conversion journeys now include their own attribution data.
- LeadForm reads from the conversion object instead of browser APIs.
- Every lead stores device information and a stable conversion event identifier.
- Database records, browser events, and GA4 events are linked through the same `event_id`.
- The system maintains accurate attribution while preserving the safeguards against duplicate conversions introduced in earlier phases.

Phase 3 transforms the project from a lead capture application into an attribution-aware conversion tracking system, providing a stronger foundation for future features such as multi-touch attribution, offline conversion imports, and server-side analytics.
