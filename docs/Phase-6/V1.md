# Complete Guide: Next.js Google Ads Lead Lifecycle Tracking System (Phase 6)

## Project Overview

Phase 6 evolves the lead measurement system from a completed conversion tracking pipeline into a complete lead lifecycle measurement system.

Phase 5 established the advertising measurement foundation:

- Google Ads conversion actions
- Google Ads Conversion Tracking
- Enhanced Conversions
- User-Provided Data delivery
- GA4 conversion events
- GTM-based measurement architecture

The Phase 5 pipeline was:

```text
User Interaction

↓

Next.js Application

↓

Lead Submission

↓

Database Insert

↓

generate_lead Event

↓

Google Tag Manager

↓

GA4

↓

Google Ads Conversion Tracking

↓

Enhanced Conversions
```

Phase 6 extends this architecture beyond the initial lead submission.

A lead is no longer considered complete after:

```text
Form Submitted
```

The system now measures what happens after the lead enters the CRM workflow.

The new pipeline becomes:

```text
Lead Submission

↓

Database Lead Created

↓

generate_lead

↓

Sales Lifecycle Updates

↓

lead_contacted

↓

lead_qualified

↓

lead_disqualified

↓

Google Tag Manager

↓

GA4 Lifecycle Events

↓

Business Funnel Analysis
```

---

# Phase 6 Goal

The objective of Phase 6 is to connect internal lead management activity with analytics measurement.

The system now answers:

- How many submitted leads were contacted?
- How many leads became qualified?
- How many leads were disqualified?
- What percentage of generated leads move through each lifecycle stage?
- Which acquisition sources produce qualified leads?

Phase 6 introduces:

- CRM lifecycle events
- Lead status tracking
- Status transition measurement
- Lifecycle Data Layer architecture
- GTM custom event routing
- GA4 lifecycle events
- Lead funnel reporting foundation

The application tracks lead states:

```text

disqualified
```

```json

  "status": "new"

```

```json
{
  "status": "contacted"
}
```

This creates:

```javascript

```

# 4. Application Lifecycle Tracking

The application sends lifecycle events only after a real status update.

Flow:

```text
Admin changes lead status

↓

API request

PATCH /api/leads/[id]/status

↓

Database update

↓

Previous status captured

↓

New status captured

↓

Lifecycle event generated

↓

window.dataLayer.push()
```

# 16. Phase 6 Design Decisions

## Why measure lifecycle events?

A submitted lead is not always a valuable lead.

The business outcome happens later.

Example:

```text
100 Leads Generated

↓

80 Contacted

↓

25 Qualified
```

Without lifecycle tracking:

```text
100 conversions
```

With lifecycle tracking:

```text
25 qualified opportunities
```

---

## Why use GTM instead of direct GA4 calls?

The application remains independent from analytics platforms.

The application only reports:

```text
Business event happened
```

GTM decides:

```text
Send to GA4

Send to future platforms
```

---

## Why keep event_id?

The same identifier connects:

```text
Lead Submission

↓

Database Record

↓

Lifecycle Updates

↓

Analytics Events
```

This creates a complete lead history.
