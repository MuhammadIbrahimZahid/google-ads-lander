1. Google Tag Manager Integration

Phase 4 introduces Google Tag Manager as the central analytics routing layer.

Previously:

Next.js

↓

GA4


Phase 4 changes this to:

Next.js

↓

Data Layer

↓

Google Tag Manager

↓

GA4


The application no longer directly controls analytics destinations.

Instead, it only reports business events.

GTM decides where those events are sent.

Benefits:

Cleaner application code
Easier marketing changes
No developer deployment required for tag changes
Better debugging visibility
Future support for additional platforms
2. Data Layer Architecture

The application communicates through:

window.dataLayer


Events are pushed using structured objects.

Example:

{
    event: "generate_lead",
    lead_source: "landing_page",
    event_id: "uuid-value"
}


The Data Layer acts as a bridge between:

Next.js Application

and

Google Tag Manager


The application does not know about:

GA4 measurement IDs
Google Ads tags
Marketing pixels
Third-party analytics tools

It only publishes events.

13. Phase 4 Design Decisions
Why use Google Tag Manager?

Application code should not directly depend on marketing tools.

GTM provides:

Flexible tag management
Faster marketing changes
Better debugging
Cleaner engineering boundaries
Why use Data Layer events?

The Data Layer creates a stable communication contract.

The application says:

A lead was generated


GTM decides:

Send this to GA4
Send this to Google Ads
Send this elsewhere

Why keep event_id?

The same identifier connects:

Browser

↓

Database

↓

Analytics


This supports:

Debugging
Deduplication
Offline conversion imports
Server-side tracking
Why validate in production?

Local development can behave differently due to:

React development mode
Debug environments
Browser extensions

Production validation confirms the real user journey.
